# Plan: A huitzilopochtli + nakon practice-box factory (`boxbuilder`)

## Goal (restated workflow)

You described four steps to "set up the box smoothly":

1. **Author** — huitzilopochtli and nakon configs are created.
2. **Plant** — nakon config is deployed to a VM (vulnerabilities planted).
3. **Score-enable** — huitzilopochtli is installed on that machine.
4. **Package & distribute** — export the machine, ready for use.

This plan builds an agent-facing orchestrator inside huitzilopochtli — a new **`boxbuilder/`** package — that automates those four steps, pairing a nakon-planted box with a huitzilopochtli scoring configuration.

### One important clarification that shapes the design

huitzilopochtli's architecture (which I confirmed in `architecture.md` §5.2 and `packaging/README.md`) is: **the *agent* (`.pyz`) runs on the box in both modes; the *engine* (server) only exists in ranked mode and lives on a separate host.** So step 3 means "install the **agent** + compiled manifest (+ rubric for honor) on the box." There is no engine on a practice box. The plan designs around this. (A self-contained "engine-on-box" ranked variant is possible later but is out of scope — flagged under Open Questions.)

### Decisions locked from our Q&A

- **No shared vuln→check registry.** The LLM agent authors *both* the nakon config (which vulns) and the huitzilopochtli scenario YAML (which checks). `boxbuilder` does **not** know the mapping; it orchestrates. This avoids mirroring an unfinished vulndb.
- **Pluggable provider** abstraction for the box target + packaging, with one concrete provider in v1.
- **Agent-first CLI**: machine-readable (`--json` on stdout, logs to stderr), consistent with nakon's recent agent-interface update.
- **Both honor and ranked modes in v1.** The compile path is mode-agnostic; deploy/packaging differ and are handled per-mode.

## Architecture: new `boxbuilder/` package

```
huitzilopochtli/
  boxbuilder/
    __init__.py            # public API (build_box, compile_box, deploy_box, package_box)
    __main__.py            # python3 -m boxbuilder ...
    cli.py                 # argparse CLI; every cmd supports --json; logs→stderr
    spec.py                # BoxSpec dataclass: scenario path, nakon config path, mode, engine cfg

      nakon-config.json                # nakon machine list + chosen vulns
```

Nothing under `agent/`, `common/`, `engine/`, or `authoring/` is modified.

## The provider abstraction (`boxbuilder/providers/base.py`)

This is the seam that makes the VM environment pluggable. v1 ships `SshProvider`; `QemuProvider` and `ProxmoxProvider` are later drop-ins.

```python
class BoxHandle:
    addr: str; user: str; password: str   # single source of truth; nakon deploy reuses these
    def run(self, cmd: str, *, timeout: int = 1800, sudo: bool = True) -> RunResult: ...
    def put(self, local: str, remote: str, mode: int | None = None) -> None: ...
    def install_init(self, kind: "systemd"|"openrc"|"none") -> None: ...
    def export(self, out_path: str, fmt: "ova"|"qcow2"|"raw") -> str: ...
    def close(self) -> None: ...

class BoxProvider:
    name: str
    def start(self, cfg: dict) -> BoxHandle: ...   # ensure box reachable; return handle
    def stop(self, handle: BoxHandle) -> None: ... # optional cleanup
```

- **`SshProvider`** (v1): `cfg = {"host","port","user","password"}`. `start()` opens a paramiko connection and verifies reachability + that `python3` is present (installs it on Alpine via `apk add python3` per `packaging/README.md:44-56`). `export()` shells out to the operator's hypervisor tooling or is a documented manual step (flagged in `--json` output as `export: "manual"` when the provider can't export itself). `install_init()` copies the unit template and runs the enable commands from `packaging/README.md:118-133`.
- **Future `QemuProvider`**: `start()` boots a cloud-init qcow2, waits for SSH; `export()` commits the qcow2/ova. **Future `ProxmoxProvider`**: clones a template, deploys via jump host (mirrors tezcatlipoca's model), exports.

**Address reconciliation:** the provider handle is the single source of the box's `addr/user/password`. When boxbuilder invokes `nakon deploy`, it writes a one-machine nakon config whose address fields come from the handle (taking the **vulnerability list** from the agent's nakon config but the **address** from the provider). This keeps the agent from having to keep two address fields in sync, and lets providers that assign addresses dynamically (qemu/proxmox) work without the agent knowing the address up front.

## The pipeline (`boxbuilder/pipeline.py`) — 4 steps

Single box spec input (`spec.py`):

```yaml
# box spec — ties together the two agent-authored files
scenario: ./linux-fundamentals.scenario.yaml   # huitz checks (mode + engine_url live here)
nakon_config: ./nakon-config.json              # nakon machine list + chosen vulns
# provider config can also be CLI flags / a separate file:
provider: {name: ssh, host: 192.168.50.10, user: ubuntu, password: ubuntu}
authoring_key: ./authoring.key     # optional; auto-generated+persisted if absent
```

Mode is read from the scenario YAML's `scenario.mode` (already a field per `validate.py:8,44`), so the spec doesn't duplicate it.

### Step 1 — `compile` (mode-agnostic)
1. Load (or generate+persist) the authoring keypair via `keys.py` (`common.crypto.signing.keypair()`).
2. `validate_scenario_yaml()` then `compile_scenario(scenario, out, priv_key)` → emits `manifest.signed.json`, `rubric.json` (honor), `engine_record.json`, `authoring_public_key.b64` into a build dir.
3. `packaging/build_zipapp.py::build()` → `agent.pyz` into the same dir.
4. Resolve the vuln set from the nakon config; shell out **`nakon build`** (`cwd=NAKON_DIR` so it can read `nakon/.env`/vulndb, exactly as tezcatlipoca does at `create-competition.py:431-453`) → bundle path. Parse the final `--json` line for `{bundle_id, path}`.

### Step 2 — `plant` (nakon deploy)
- Write a one-machine nakon deploy config: vulns from the agent's nakon config, address from the provider handle.
- Shell out **`nakon deploy --bundle <bundle> --config <derived> --json`** (no vulndb needed at this stage). Parse `{ok, failures, machines[].steps}`.

### Step 3 — `install` (score-enable the box)
Put files to the provider handle's box under `/opt/huitzilopochtli/` (per `packaging/README.md:11-24`):

| File | Honor | Ranked |
|---|---|---|
| `agent.pyz` | ✅ | ✅ |
| `manifest.signed.json` | ✅ | ✅ |
| `authoring_public_key.b64` | ✅ | ✅ |
| `rubric.json` | ✅ (local scoring) | ❌ (stays off-box) |
| `agent_config.json` | mode=honor, rubric set, identity null | mode=ranked, rubric null, identity_path set, checkin_interval_s set, engine_url set, enrollment_token set |
| init unit | systemd/openrc via `handle.install_init()` | same |

`artifacts.py` generates `agent_config.json` per mode against the real `AgentConfig` shape (`agent/config.py:9-19`). Ranked-only sub-steps (`engine.py`), before writing `agent_config.json`:
- Ensure the engine has the scenario record: `POST /admin/scenarios` with `engine_record.json` (header `X-HUITZILOPOCHTLI-Admin-Token`), or rely on the engine's `HUITZILOPOCHTLI_ENGINE_RECORD_PATH` startup seed.
- Mint a one-time enrollment token: `POST /admin/tokens {scenario_name, ttl_s}` → embed `token` into `agent_config.json.enrollment_token` (consumed once on first boot per `agent/config.py:35-37`).
- Verify outbound reachability from box to `engine_url` (warn, don't fail — the box may be offline at build time).

(For honor mode none of the engine wiring applies.)

### Step 4 — `package`
- `handle.export(out, fmt)` → image path (provider-specific; `SshProvider` reports `"manual"` with instructions if it can't self-serve).
- Run `packaging/rearm.py` semantics if a take-home replay reset is wanted (optional flag).

## CLI surface (`boxbuilder/cli.py`, agent-facing)

`python3 -m boxbuilder <cmd> --json` everywhere; **result → stdout (single JSON line for parseability, like nakon), progress → stderr.**

```
boxbuilder compile   --spec box.yaml [--out artifacts/] [--json]
boxbuilder plant     --spec box.yaml --bundle-from-compile artifacts/ [--json]
boxbuilder install   --spec box.yaml --artifacts artifacts/ [--json]
boxbuilder package   --spec box.yaml --artifacts artifacts/ --out box.ova [--json]
boxbuilder build     --spec box.yaml [--from-step compile|plant|install|package] [--json]
```

- `build` runs all four with a resumable checkpoint (`--from-step`, mirroring tezcatlipoca's `--from-phase`).
- Each subcommand is independently idempotent and inspectable, so an agent can pause/verify between steps.
- Flags also accept the two inputs directly (`--scenario`, `--nakon-config`, `--provider*`) without a box.yaml.
- `--nakon-dir` (default: `$NAKON_DIR` then `../nakon`) for the build shell-out cwd.

## nakon integration contract (`boxbuilder/nakon.py`)

- **Build:** `subprocess.run([sys.executable,"-m","nakon","build","--config",cfg,"--out","bundles","--json"], cwd=NAKON_DIR, capture_output=True, text=True)` → `json.loads(stdout.splitlines()[-1])` (exactly tezcatlipoca's contract at `create-competition.py:431-453`). Requires vulndb reachable + `nakon[build]`.
- **Deploy:** `nakon deploy --bundle … --config … --json` → parse `{ok, failures}`; `--strict` maps to non-zero exit. Requires only `nakon[deploy]` (paramiko), no vulndb.
- boxbuilder never imports nakon as a library (avoids coupling to nakon internals); it treats nakon as a CLI dependency, consistent with how tezcatlipoca consumes it and with nakon's documented embed contract (`README.md:257-272`).

## Authoring-key handling (`boxbuilder/keys.py`)

`compile_scenario` requires `authoring_private_key: bytes`. Policy:
- If `--authoring-key <path>` given, load it.
- Else auto-generate (`signing.keypair()`), persist to the artifacts dir (`authoring.key`, mode 0600) so the same box rebuilds with a stable manifest signature, and print the path in `--json` output. Key custody stays with the build (author/CI), never on the box — matching the invariant noted at `compile.py:111-115`.

## Phased implementation (milestones)

1. **M1 — Skeleton + compile.** `boxbuilder/` package, `spec.py`, `cli.py` `compile` subcommand: reuses `compile_scenario` + `build_zipapp.build` + `nakon build` shell-out, emits artifacts, `--json`. Unit tests for spec/keys/nakon wrappers.
2. **M2 — Provider abstraction + SshProvider + plant.** `providers/base.py`, `providers/ssh.py`, `nakon.py` deploy wrapper, `plant` subcommand, address reconciliation. Integration test with FakeProvider.
3. **M3 — Install (both modes).** `artifacts.py` (per-mode `agent_config.json` + file placement), `install` subcommand for honor. `engine.py` + ranked install (scenario upload + token mint against a stubbed engine).
4. **M4 — Package + unified `build`.** `package` subcommand, `build` with `--from-step` resumability, end-to-end integration test.
5. **M5 — Docs & example.** `boxbuilder/README.md`, repo-root `AGENTS.md`, `examples/` worked box.

(M1–M2 are independently useful: an agent can compile + plant even before install/package land.)

## Out of scope / Open Questions

- **No shared vuln→check registry** (per your decision). If vulndb later matures, a registry could be added without changing `boxbuilder`'s contract (the agent just stops hand-authoring checks).
- **Engine co-location:** ranked boxes currently need a separate running engine. If you want a *self-contained* ranked box (engine on the box), that's a new mode variant — not built here; flagged for later.
- **Multi-box / multi-team competitions:** this plan targets single practice boxes (honor take-homes + individual ranked practice). tezcatlipoca already covers multi-team ranges; `boxbuilder` is intentionally complementary, not a replacement.
- **Image export** for `SshProvider` is environment-dependent; v1 may report `export: "manual"` with instructions rather than self-export. A `QemuProvider`/`ProxmoxProvider` later would make export fully automatic.
- **Provider name** (`boxbuilder`), CLI module name, and box-spec format are adjustable if you prefer a deity-themed name or a different shape.
